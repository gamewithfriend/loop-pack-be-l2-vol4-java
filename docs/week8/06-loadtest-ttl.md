# 06. 토큰 TTL 부하 실험 — 시뮬레이션 결과 & D1 개정

`WaitingQueueTtlSimulationTest`(결정적 시뮬레이션 하니스)로 토큰 TTL(D1)을 스윕해 처리량/UX 트레이드오프를 측정했다. 결론에 따라 **D1을 60초 → 30초로 개정**한다.

## 왜 HTTP 부하가 아니라 시뮬레이션인가

토큰 TTL은 "발급된 토큰이 **안 쓰일 때**(이탈·느린 주문)"만 효과가 나타나는 레버다. 모든 가상 유저가 토큰 받자마자 즉시 주문하는 단순 HTTP 부하는 TTL 효과가 0으로 나와 오히려 오해를 부른다. 그래서 **이탈률·주문지연 모델**을 넣은 시뮬레이션으로 측정한다. 정책 산정(maxActive·배치=활성까지 리필)은 실제 `ThroughputPolicy`를 그대로 사용한다.

## 모델

- 플래시 크라우드 **N=5000명**이 t=0 동시 진입, `maxActive=30`, 스케줄러 틱 2s.
- 유저 특성(고정 시드로 1회 생성 → 전 TTL 런에서 재사용, 공정 비교):
  - **이탈자 15%** — 토큰을 받아도 주문하지 않음(탭 닫음). 슬롯을 TTL 만료까지 점유 후 떠남.
  - **정상 85%** — 토큰 수령 후 주문 지연(지수분포, 평균 6s). 지연 > TTL이면 만료로 **바운스 → 재진입**(최대 5회, 초과 시 실패).
- 결정적(seed=42)이라 재현 가능. 유저 특성이 모든 TTL에서 동일하므로 TTL만의 효과가 분리된다.

## 해석

**TTL은 양날의 검이고, 이 조건에선 30s가 최적이다.**

- **TTL 너무 짧음(8s)**: 6초보다 느린 정상 유저가 계속 바운스 → **1058명 실패**, 토큰 3.2배(10290) 낭비. UX 최악.
- **TTL 너무 김(60/120s)**: 이탈자 748명이 슬롯을 각 60~120초 점유(squatting) → 새 입장이 막혀 **처리량 2.25→1.05/s 반토막**, 배수시간 31→67분.
- **TTL=30s 스위트스팟**: 배수시간 최소(31분), 처리량 최고(2.25/s), 실패 28명(≈0), 토큰 발급 효율 1.22배.

**시사점**: 초안 기본값 D1=60s는 처리량 관점에서 과했다. 15% 이탈 가정하 60s는 30s 대비 배수시간을 33%(31→42분) 늘리면서 겨우 28명의 엣지 실패만 제거 — 트레이드오프가 맞지 않는다.

**p95 대기 주의**: TTL이 짧을수록 p95가 낮아 보이는 것은 생존자 편향이다(느린 유저가 실패로 빠지고 "완주자만" 집계). 주 지표는 **배수시간·처리량**으로 본다.

## 결정(개정)

- **D1: 토큰 TTL 60초 → 30초.** `application.yml` `waiting-queue.token-ttl-seconds: 30`, `WaitingQueueProperties` 기본값 30.
- 단, 최적 TTL은 **이탈률에 민감**하다(이탈↑ → 슬롯 회수 위해 더 짧은 TTL 유리). 실서비스 이탈률/주문지연 관측치가 확보되면 재튜닝한다. 현재 30s는 이탈 15%·지연 6s 가정 기준.
- 파라미터는 모두 yml 외부화라 코드 변경 없이 조정 가능.

> 재현: `./gradlew :apps:commerce-api:test --tests "com.loopers.domain.waitingqueue.WaitingQueueTtlSimulationTest"` → JUnit `system-out`에 표 출력.
